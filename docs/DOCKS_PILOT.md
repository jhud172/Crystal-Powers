# Crystal Docks HTTPS pilot

`render-docks-pilot.yaml` defines a standalone free Render web service and a new PostgreSQL 17 database in Frankfurt. It uses the website's existing Dockerfile and Docks integration branch. Configure the Blueprint to create new resources and keep automatic sync off. The database denies external connections and grants the service its own connection settings. Render generates the application encryption key. Media uses temporary local storage. The pilot starts with outbound mail, paid billing and online AI disabled.

Use only synthetic accounts and test provider credentials. Configure a separate Google OAuth client, the Stripe sandbox webhook and test Prices, and a controlled mail sender before those tests. Verify the actual HTTPS origin after deployment before registering callbacks. The Docks pilot profile adds a search-engine exclusion header. Treat the endpoint as publicly reachable.

The pilot only signs in approved test accounts. Set `DOCKS_PILOT_ALLOWED_EMAILS` on the pilot service to a comma-separated list of exact controlled addresses. Enable the intended provider after setting that list. Unlisted email requests return the same generic response as other code requests, and no email or challenge is created. Google sign-in also requires verified ownership of a listed address. Removing an address blocks further use of its Docks sessions on the pilot. The production profile uses normal customer registration.

Email sign-in defaults to disabled. Keep `MAIL_PROVIDER=disabled` on the hosted pilot so other website mail stays off. In the pilot service's secret settings, add `DOCKS_PILOT_RESEND_API_KEY` with a dedicated sending-only Resend key scoped to the verified domain. Set `DOCKS_PILOT_MAIL_FROM` to a sender on that domain, set the exact recipient allowlist, and set `DOCKS_EMAIL_ENABLED=true`. The pilot sender also delivers owner password reset emails for accounts already enrolled in MFA. General website mail stays disabled. Local SMTP fixtures still work with the numeric loopback host `127.0.0.1` or `::1`.

Check `GET /api/docks/auth/email` before requesting a code. A value of `true` confirms the application has the required settings. Confirm delivery and single-use exchange with a controlled recipient. Removing the pilot key and turning off `DOCKS_EMAIL_ENABLED` disables the hosted test.

The release build passed a local browser and SMTP check using the environment switch and a loopback-only recipient fixture. It exercised the real SMTP transport, code exchange, report sign-in and sign-out, and verified the page's unavailable and Google-only states. The hosted pilot also verified Resend delivery and single-use code exchange for both approved test accounts.

For Google sign-in, use a Web application client in a dedicated Crystal Docks Google Cloud staging project. Register exactly `https://crystal-docks-pilot-xpyl.onrender.com/api/docks/auth/google/callback` as the authorised redirect URI. The server requests `openid email`. Docks checks the verified email against `DOCKS_PILOT_ALLOWED_EMAILS` before issuing a session. [Google OAuth setup](https://developers.google.com/identity/protocols/oauth2/web-server#creatingcred)

Set `DOCKS_GOOGLE_CLIENT_ID` and `DOCKS_GOOGLE_CLIENT_SECRET` in the Render pilot environment and keep `PUBLIC_URL` set to the exact pilot HTTPS origin. Use a separate OAuth project and client for production. [Google production OAuth guidance](https://developers.google.com/identity/verification/authentication-policy-compliance)

After the pilot reports Google as enabled, sign in through `/docks/reports` with an approved Google identity and verify that private reports load for that account. Generate a Windows sign-in code from the same session, redeem it in the staging desktop preview, and confirm that a second redemption fails. Verify that an unlisted account receives no Docks session. The current pilot reports Google as disabled and rejects the sign-in start request.

In the owner studio, open **Account security → Crystal Docks release configuration** to see which sign-in methods, checkout plans, subscription portal, online explanations and installer version the server offers. Check **Crystal Docks payment review** for queued deliveries that need attention. Confirm provider and package behaviour with the pilot before rollout.

The Windows app, download page and reports page link to `/docks/support`. It uses the existing support intake and works before a customer can sign in. The browser link carries no account details or diagnostic references. Customers review what they enter and can include a reference they previously chose to share. The pilot disables outbound mail until delivery is configured.

Run `./scripts/verify-docks-public-routes.ps1` in PowerShell 7 to check the hosted pilot while sign-in and the download feed are disabled. Pass `-EmailEnabled` or `-GoogleEnabled` to check the expected provider flags after configuration. The script checks the anonymous routes and indexing headers. Complete the sign-in journeys separately with approved test accounts.

Free Render PostgreSQL expires after 30 days and the free web service sleeps when idle. [Render free services](https://render.com/docs/free)

## Release dependency review

The packaged website uses Jackson 2.21.7. The runtime scan cleared the seven Jackson advisories found in 2.21.5. It still reports two Spring MVC 6.2.19 advisories for XSLT rendering and Server-Sent Event view fragments. The website source uses neither facility. The direct fixes on the existing Spring 6.2 line require Enterprise Support.

On 25 November 2026, the full website release build and 320 backend tests passed against the Docks integration containing the support form. The packaged application also passed the Windows customer journey over local HTTPS with PostgreSQL 17.10 and test mail. OSV returned the same two Spring advisories across 72 resolved Maven runtime dependencies. The production npm audit and the Windows NuGet audit returned no advisories. [Spring XSLT advisory](https://spring.io/security/cve-2026-47884/) and [Spring event fragment advisory](https://spring.io/security/cve-2026-47890/)

## Database access

Docks uses the server's PostgreSQL role and application authorisation. Migration `V105__protect_docks_database.java` enables row-level security for its existing tables and revokes direct table access from `PUBLIC`, `anon`, `authenticated` and `service_role` when those API roles are present. The application's table owner continues to serve authorised requests. Keep new Docks tables out of the hosted Data API by applying the same protections. [Supabase Data API hardening](https://supabase.com/docs/guides/database/hardening-data-api)

The PostgreSQL 17 test granted the three hosted API roles default table privileges before Flyway ran. All 30 Docks tables had row-level security afterwards and none of the three roles retained direct table grants. The signed webhook smoke still passed using the application's database connection.

Run `./gradlew postgresTest --tests '*DocksCustomerJourneyTests'` with the repository's disposable loopback PostgreSQL settings to exercise the customer HTTP journey. Local PostgreSQL 17.10 passed email-code exchange and replay rejection, device enrolment, Free and trial entitlements, report consent and isolation, owner access with customer approval, independent log and research withdrawal, and session revocation. The test captures customer email in memory. It enrols a synthetic owner with an authenticator, signs in with the password and a one-time recovery code, and obtains the application CSRF token before reading a shared report. It verifies that the customer sees the view event for both summaries and diagnostic logs. The staged owner read still requires an authorised staging owner session.

The same PostgreSQL HTTP test verifies owner-only key issuance with CSRF protection, a one-device limit, account binding, transfer after removing the old device, extension from the existing expiry, and immediate loss of repair entitlement on suspension and revocation.

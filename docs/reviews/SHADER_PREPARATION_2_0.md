## Change and reason

The [GPU/startup review](GPU_STARTUP_REVIEW_2_0.md) traced cold Home long tasks around one second to synchronous shader-status reads. `PreparedScene.tsx` now compiles the mounted main scene, polls native program completion through [KHR_parallel_shader_compile](https://registry.khronos.org/webgl/extensions/KHR_parallel_shader_compile/), then permits the first main draw. A positive React Three Fiber frame priority owns that draw; model/controls still update before it. Readiness is announced after the draw, keeping the original still artwork and disabled unready controls in place while preparing. The procedural environment still owns its separate cube-map pass.

The helper owns its ten-millisecond polling timer and cancels it on revision changes/unmount, with a ten-second deadline and context-loss/query-error fallback. This follows the non-blocking completion contract while keeping Three's shader debugging enabled. It uses the renderer's public program information, validates native handles and isolates the type assertion required by Three's `unknown` program type. Unsupported drivers yield once and retain regular rendering; no speed guarantee applies to that fallback. No renderer/library monkey patch, dependency, route, API, schema, material, geometry, camera, quality profile or animation contract changed.

An initial prototype used Three's `compileAsync`. Inspection showed its internal timer polls material properties and offers no cancellation; disposing a stage while its promise is pending could leave the library polling disposed properties. That was an implementation concern found in source, not claimed as a reproduced production failure. The final helper owns polling instead. Controlled delayed compilation, route cancellation, thrown query errors/retry and missing capability all pass in the actual browser.

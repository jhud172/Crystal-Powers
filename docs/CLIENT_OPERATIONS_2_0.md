# Client requests, communication and billing — 12 October 2026

## Objective and experience

James confirmed that the hub is where his team handles website requests, updates their progress and contacts each client. Payments must be easy through the site, including ongoing payments when agreed. The client experience should centre on three tasks: see the current progress, send/read a message and pay/manage an agreed bill. Staff need a persistent inbox, assignment, internal notes, customer-visible updates, invoices and payment state alongside private team communication.

## Implementation boundaries and ownership

Public enquiry routes and DTO validation remain. Valid submissions are saved to an additive request store before notification; an optional idempotency key prevents the same submission creating duplicate requests when retried. Existing success/message/fieldErrors fields remain, with a request reference added. Preserve upload validation and the existing email transport. Staff reads/writes require current workspace/capability checks. Public callers cannot read requests from guessed IDs or choose staff/customer roles.

Requests, messages, status/history and private attachment metadata belong to repositories/services with Flyway migrations. Team support controllers use `/api/team/support`; frontend surfaces belong to `features/team`. A separate client identity and private `/client` surface will own client messages, progress and billing, without exposing internal notes, staff channels or other clients. Client routes must be private/noindex, with appropriate authentication, session expiry/recovery, token safety and per-client resource checks.

The business is currently one protected-owner workspace. Incoming requests received before workspace provisioning remain unassigned in storage and can only be claimed through the authorised singleton-business support service. This is not a generic multi-tenant ingress API; callers never submit a workspace ID.

## Communication and workflow

Store enquiries and accepted private files, then track team notification separately. Staff can assign active team members, update status/progress/next steps, write an internal note or create a customer message. Only customer messages can enter customer-facing email/portal output. Delivery must show saved/sending/sent/failed distinctly; retries retain one message and use provider idempotency where supported. Email recipients come from the stored request/client, not an unrestricted staff form. Messages remain escaped plain text initially.

Uploads remain private and quarantined for moderation. Downloads require permission and attachment disposition; no content is automatically published. Moderators review files without automatically gaining enquiry/contact access. Storage/provider failures must not claim receipt, moderation, publication or delivery. Existing limits and private media architecture must be respected.
